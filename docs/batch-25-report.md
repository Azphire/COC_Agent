## 代码与发现的问题

新增 `backend/scripts/check_batch25.py`，复用既有 Windows 启动、正常停机、HTTP 和导出驱动；新增 `check_batch25_evidence.py`。原驱动只增加可指定数据库路径的兼容入口。新驱动独立解析现有 `Settings`／`ModelSettings`，不再继承固定 OpenAI 初始化。

- 请求在发送前原子落盘；保留原文本、`client_request_id`、cycle/check/roll ID、事件范围、骰前后状态和工具回执。续跑查询原提交事件；已结算骰与已经完成的揭示、拿取均不再执行。回合完成但无对应回应或调查结果不能通过。
- 摘要、保存载入、恢复后回顾、恢复后继续分别记录；`restores` 非空或行动文本曾出现均不能替代实际提交及回应。审计逐项输出 `passed / failed / not_run / blocked`，保留证据路径；未发生的骰分支标记未覆盖。
- 三次墙面观察没有产生示意图揭示。前两次暴露了当前候选遗漏无需检定的隐藏实体；`preparation/search.py` 将本地 `automatic` 对象纳入候选，条件、揭示和库存仍由原服务判定。修复后第三次自然观察仍未发现示意图，原回应完整保留，**不宣称该自然路径已通过**。此时没有调查骰，随后沿批准相邻通路调查座位；没有重开房间或替换失败骰。
- 原摘要驱动只调用一次增量重建，首次只覆盖到 #111。补齐按覆盖序号继续处理的能力，每次最多六个窗口；无进展保留失败。追到后续事件后，压缩正文仍遗漏便签内容，因此在 `memory/recovery.py` 复用当前公开实体、库存和可见事件，加入有长度上限的状态核对段（`memory/state_facts.py`）。该段保留实际检定、已知文字和实例所有者，不从玩家意图或隐藏原文推导事实，不作为世界状态写入来源。
- 两轮摘要复验先归档旧摘要、恢复及回应记录，再仅重做受影响的摘要／恢复／回顾／继续阶段。原检定与库存回执保持唯一。没有扩展检索架构或主持文风开发。
- 最后复核发现“展开便签再看文字”被系统归类为回顾。旧版审计只要求实际回应，会错误放行这种情况；已补充正反例，继续阶段现须有动作计划及真实转场事件。旧回顾记录保留，另提交一次带着便签进入相邻车厢的自然行动。
- 实际转场后，现有导航服务将摘要正文包装为带 `current_scene_node_id`／`heading_path` 的 JSON。审计保留存档正文的严格相等比较，并按此既有格式比较当前摘要的同一 ID 和原正文；正文改变或摘要缺失仍判失败。没有为通过审计修改存档、摘要或导航服务。
- 完成态续跑又暴露了脚本会用当前摘要覆盖存档前摘要证据的问题。已冻结完成阶段的摘要记录，并新增回归；被覆盖的日志保存在 `summary-journal-recovery/`，从自动生成的续跑前备份恢复原摘要记录，来源见该目录 `provenance.json`。只修复证据日志，没有改游戏数据库。最终 launcher 13 再次续跑，新增模型调用 **0**，原请求、步骤记录及摘要完全不变，见 `resume-verification.json`、`resume-verified.log`。
