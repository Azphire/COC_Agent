### 本批真实时间线与窄优化

同一次请求最终102次mutate合计159.419s，其中广播121.731s；广播内305次完整snapshot构建合计115.940s，单次最高719ms。三条连接为两个真实玩家窗口和记录driver，权限身份相同。房间锁等待累计0.500s、事务begin 0.624s、commit 1.966s。**本次额外等待的显著路径是重复快照构建**，不能外推第50批未保存的完整时间线。

上下文初次准备12.062s、最终准备7.422s、schema最终准备0.234s；这些span包含其内部mutate／广播，不能与上面再次相加。正式事件创建约258.989s，事务提交点259.038s；三连接正式事件入队分别晚于commit约20／403.5／761.8ms，入队不等于DOM。全部可关联span闭合且无失败；无法绑定本次cycle的房间span单列保留。

调用记录内5次on_call累计6.389s、adapter累计92.858s、请求准备0.154s、终态验证0.528s。持久调用记录中的on_result结束字段为null（该记录在回调内部落盘），JSONL另有5次 `model.call_audit` 合计5.235s；不能将null写成0。无法绑定cycle的同房间阶段另有9次broadcast／10.732s、27次snapshot／10.280s，汇总单列，没有混入上述cycle统计。

真实采集结束后才实施两项窄优化：

- `mutate(..., internal_only=True)`仅用于已核实的调用审计／技术计数／生成run内部保存；无事件时省略广播，任何新增事件都强制执行原广播。审计、事务和锁仍保留，实际阶段及正式事件仍及时发布。
- 每次broadcast内按 `(member_id, is_host)` 复用同一权限的完整快照；每连接仍独立发送事件、snapshot与synced并记录入队时间，不跨广播或重连缓存。不同玩家／host独立构建；`snapshot.reuse`与真实build分别记账。

同条件离线复测（3审计写入、2不同玩家、零模型）：完整snapshot构建6→0，审计墙钟938→266ms，原审计仍全部持久。时钟有约15–16ms粒度，机器负载未严格控制；构建次数减少是直接证据，不据此宣称端到端真实提速。下述唯一真实运行在优化前完成，未为性能改动再次调用模型。

同身份投影复用的独立测量：3个同玩家连接，完整view从3次／45.545ms变为1次／14.479ms，另2次标记reuse，仍送达3份相同snapshot。不同身份不复用；后续广播与重连重新读取当前状态。
